# LazyMind 插件机制学习

> 本文讲的是实现方式，不展开插件的配置用法。

## 一句话总结

LazyMind 的插件机制不是传统意义上的“注册一段回调代码”，而是一条由 YAML 编译成状态机、由数据库事实投影出运行状态、再由 Python 和 Go 协作驱动多 Agent 执行的链路：

```text
plugin.yaml + state.yml
        |
        v
Go 编译成 CompiledStateGraph（含校验、图哈希）
        |
        v
DB 记录 attempts / slot revisions / route decisions
        |
        v
Go Project() 计算 reachable / ready / blocked / stale
        |
        v
Python 把合法候选暴露成 ChatAgent 工具
        |
        v
Go 提交 SubAgent 任务 -> Python 执行单步 -> artifact 事件回流 -> Go 持久化
        |
        v
auto 模式由 Python DriverAgent 评估，Go 把评估送回 ChatAgent
```

## Python 和 Go 各自负责什么

| 层 | 负责的事 | 核心代码 |
|---|---|---|
| Python | 插件文件加载、脚本工具导入、ChatAgent 工具生成、preflight、SubAgent 执行、artifact 工具、DriverAgent 评估 | `algorithm/lazymind/chat/plugin/`、`algorithm/lazymind/chat/engine/subagent/` |
| Go | YAML 编译、状态投影、transition 校验、session/attempt/route 持久化、任务派发、终态处理 | `backend/core/plugin/`、`backend/core/plugin/graphengine/` |

Python 侧不是薄壳。真正让 LLM 能“看到”插件、执行一步、保存产物、评价质量的部分都在 Python 里。Go 负责的更多是状态权威和并发安全。

## 1. 插件加载：Python 是入口

入口是 `algorithm/lazymind/chat/plugin/plugin_loader.py`。

启动时 `load_all()` 扫描 `plugins/<plugin-id>/`，每个目录构造成一个 `PluginSpec`。构造时做四件事：

1. 读 `plugin.yaml`，得到注册信息、slot 定义、UI 布局、工具声明。
2. 读 `scenario.md`、`state.yml`、`driver.md`，分别作为 ChatAgent、SubAgent、DriverAgent 的输入。
3. 把 `state.yml` 里两种步骤写法（map/list）统一成同一份内部结构。
4. 根据 `tool_scripts` 动态导入插件脚本工具。

动态导入的关键实现是：每个插件脚本用独立 module name 加载，避免不同插件间的函数名互相污染；再按声明好的函数名取出 callable，放进 `{函数名: callable}` 映射：

```python
# plugin_loader.py
module_name = f"_plugin_script_{plugin_id}_{script_path.stem}"
spec = importlib.util.spec_from_file_location(module_name, script_path)
module = importlib.util.module_from_spec(spec)
spec.loader.exec_module(module)
```

所以插件作者写 `tools.py` 时不需要继承任何框架基类，只需要把函数名写进 `plugin.yaml` 的 `tool_scripts[].functions`。这个映射之后会被 SubAgent runner 按 step 的 `tools` 列表查找。

关键位置：

- `PluginSpec.__init__`：读取和校验插件文件
- `PluginSpec._load_script_tools`：动态导入脚本工具
- `load_all`：启动时建立插件注册表

## 2. 编译：Go 把 YAML 变成可执行图

Python 读 YAML 是为了生成 Agent 工具和步骤配置；Go 读 YAML 是为了得到真正的运行图。

`backend/core/plugin/graphengine/compiler.go` 的 `Compile()` 输入是 `plugin.yaml`、`state.yml` 和 scenario，输出 `CompiledStateGraph`：

- 每个 step 变成节点，节点带输入表达式、输出、必产输出、`skip_if`、路由模式；
- 每条 transition 变成控制边，`when` 保留为自然语言文本；
- 每个 slot 进入素材生产者表，记录它由哪个 step 产生，还是外部输入；
- 编译结果附带校验诊断和图哈希。

编译期强校验的关键规则：

- 图必须是 DAG，禁止自环；
- 一个 slot 只能有一个 producer；
- step 不能同时消费和产出同一个 slot；
- step 不能产出未在 `plugin.yaml` 声明的 slot；
- 每个非 external slot 必须有 producer。

图哈希是运行期一致性的基础。已发布/远程插件会把编译好的图存在 plugin revision 里，session 启动时绑定该修订；后续 transition 必须带相同 `graph_hash`，否则拒绝。内置插件走兼容路径：Go 从 Python 接口取原始 YAML，运行时重新编译。

## 3. 状态投影：Go 是状态权威

`backend/core/plugin/graphengine/projector.go` 实现纯状态计算，不依赖 LLM。

每次投影从数据库读三类事实：

- attempts：每步执行状态、是否已 stale；
- selected slot revisions：哪些素材有效；
- route decisions：某个源节点实际激活/剪枝/旁路了哪些边。

投影算法可以简化为：

```text
从 __start__ 激活出边
对每个 succeeded attempt，继续激活它的出边
对每个被激活节点：
    输入素材表达式满足 -> ready
    输入素材不满足     -> blocked
```

同时还得到 past、current、reachable、stale、pruned、bypassed。session 只在到达 `__end__`、没有当前任务、没有 ready/blocked 节点时完成。

transition 提交时，Go 会在数据库事务里：

1. 锁住 session；
2. 重新加载 session 绑定的图；
3. 用最新事实重新 projection；
4. 校验 `state_version` 和 `graph_hash`；
5. 校验目标 step 是 reachable 且 ready；
6. 创建 attempt、输入 witness、route decision，递增版本；
7. 派发任务。

这一层保证了“LLM 只能选择合法路径”，以及两个并发请求不会重复启动同一个状态。

## 4. ChatAgent 工具：Python 按 Go 的投影生成

`algorithm/lazymind/chat/plugin/plugin_manager.py` 负责把插件机制暴露给 ChatAgent。

### 冷启动阶段

没有活跃 session 时，`build_cold_start_tools()` 为每个已加载插件生成一个 `trigger_<plugin>` 工具：

- docstring 由 `when_to_use` + `description` 生成，让模型知道何时该触发；
- 工具本身不创建 session；
- 调用后会执行一次 Python preflight，用 LLM 判断请求是 `ready`、`need_information` 还是 `not_applicable`；
- 返回 ready 后，`prepared_plugin` 和 `launch_plan` 写进当前 `agentic_config`；
- 如果模型没有在同一轮调用 advance 工具，框架会强制再跑一次 ReAct，再不行就按 launch_plan 确定性提交。

### 活跃 session 阶段

`resolve_plugin_injection()` 在每次请求开始前构建插件工具。`build_advance_step_tool()` 和 `build_advance_step_and_hand_off_tool()` 会先请求 Go 的 projection 接口：

- `ready` 列表成为“可以推进的下一步”；
- `past` 列表成为“可以 rewind 回去的步”；
- 工具 docstring 里只会出现这些候选。

也就是说，ChatAgent 从工具描述里看到的不是完整 state.yml，而是 Go 当前允许它做的选择。

## 5. 提交一次 transition

Python 侧先渲染步骤 objective。这里有一个容易误会的点：`{{user_input}}` 和 `{{runtime_instruction}}` 会被替换，但 `{{slot}}` 不会逐个替换成文本。slot 内容之后由 SubAgent runner 以“已有素材摘要”的形式注入 prompt。

```python
# plugin_manager.py
prompt = step_config.get('prompt', '')
prompt = prompt.replace('{{user_input}}', user_input)
prompt = prompt.replace('{{runtime_instruction}}', runtime_instruction)
```

然后 `_trigger_plugin_step()` 通过 HTTP 向 Go 提交 transition。请求里带：

- `command_id`：用于超时后查询，避免重复提交；
- `task_id`、`session_id`、`step_id`；
- `expected_state_version`、`graph_hash`；
- 渲染后的 objective、用户输入、附件、filters、LLM/tool 配置；
- 如果是批量执行，一次带多个 target。

Go 接受后返回新的 projection 和 task id。同步的 `advance_step` 会再轮询 Go 的 task 状态直到终态；异步的 `advance_step_and_hand_off` 直接结束当前 ReAct turn，等任务完成后再触发下一轮。

## 6. SubAgent 单步执行：Python 是执行器

Go 创建任务后，通过 `/api/subagent/run` 调用 Python。

`algorithm/lazymind/chat/engine/subagent/runner.py` 是核心：

### 工具解析

`_resolve_runtime_tools()` 把 `state.yml` 某步声明的工具名解析成实际 callable：

1. 先在当前插件的脚本工具表里找；
2. 找不到再查全局 `DEFAULT_TOOLS`；
3. `save_artifacts`、`get_artifact`、`list_artifacts`、`patch_artifact` 等基础设施工具始终注入。

### Prompt 构造

`_build_subagent_plan()` 构造单步 prompt：

- SubAgent 角色说明；
- 当前 step objective；
- 从 session 已选 slot revision 生成的已有素材摘要；
- 输出契约：哪些必产、哪些可选、list slot 是 append 还是 overwrite；
- 用户附件、意图约束、partial retry 提示。

所以 SubAgent 看不到完整插件图，它只知道自己这一步该干什么、能调用什么工具、必须产出什么。

### 产物保存

`algorithm/lazymind/chat/engine/subagent/tools.py` 的 `save_artifacts` 先校验 key 是否在该步声明的输出里，然后记录到当前 context，并发出一条 SSE artifact 事件：

```text
Python SubAgent save_artifacts
  -> SSE artifact 事件
  -> Go subagent runner 持久化 sub_agent_artifacts
  -> Go plugin artifact hook 映射成 slot revision
  -> 前端实时收到 plugin_artifact_updated
```

slot 的 list/single、sort_order、selected revision、human/AI change source 都由 Go 侧统一处理。

## 7. 终态处理：DriverAgent 在 Python

SubAgent 完成后，Go 的 `OnSubAgentDone` 做状态收尾：

- 更新 attempt 状态；
- 成功后冻结 route decision；
- 重新 projection，判断 session 是否完成；
- auto 模式调用 DriverAgent；
- dynamic 模式发送 `step_waiting`。

DriverAgent 的实现也在 Python，`algorithm/lazymind/chat/plugin/driver_agent.py`。

`_build_driver_prompt()` 取插件 `driver.md`，没有则用内置默认 prompt，并强制附加“只输出 1-2 句自然语言、不要 PASS/RETRY 等机器码”的约束。`_build_driver_plan()` 把以下内容组合成一个评估 prompt：

- driver.md；
- 当前 step 的 `acceptance_criteria`；
- SubAgent 的执行结果；
- 当前 session 的素材摘要；
- 用户附件列表。

Python 评估完成后返回一段自然语言。Go 收到后把它当作合成用户消息，触发下一轮 ChatAgent。所以最终“推进、重试、回溯”的决策始终在 ChatAgent，DriverAgent 只提供事实和诊断。

## 8. 重试和回溯：stale 语义

`retry` 和 `rewind` 不是图上的回边。

Go 会把目标 attempt 标成 stale，然后沿 `PluginAttemptInputBinding` 找到所有消费过该 attempt 产物的下游 attempt，递归地把：

- 下游 attempt；
- 这些 attempt 产生的 slot revision；
- 依赖这些 revision 的 route decision；

都标成 stale。之后重新 projection，下游自然从 ready 变成 blocked/stale，上游重新变成候选。

`partial_indices` / `sort_order` 是另一种重试：不废弃整个 slot，而是只覆盖 list 中的指定位置。

## Python 侧值得重点看的代码

如果后面要一个个点深入，建议按这个顺序读 Python：

1. `algorithm/lazymind/chat/plugin/plugin_loader.py`
   - 插件文件如何变成 `PluginSpec`；
   - 脚本工具如何被动态导入。
2. `algorithm/lazymind/chat/plugin/plugin_manager.py`
   - trigger/preflight 如何生成；
   - advance 工具如何基于 Go projection 构造；
   - transition 请求如何提交。
3. `algorithm/lazymind/chat/engine/subagent/runner.py`
   - 单步 prompt 如何构造；
   - 工具如何按 `state.yml` 解析；
   - ReAct 执行和 SSE 事件如何产生。
4. `algorithm/lazymind/chat/engine/subagent/tools.py`
   - `save_artifacts` / `get_artifact` / `patch_artifact` 如何实现；
   - 模型产物如何变成 context 中的 artifact 事件。
5. `algorithm/lazymind/chat/plugin/driver_agent.py`
   - DriverAgent 的 prompt 如何组装；
   - 为什么它的输出是自然语言而不是机器判定。

## 建议后续逐个深入的点

- preflight 为什么必须是无副作用的，以及 `ready / need_information / not_applicable` 如何归一化；
- Go 的 route decision 在什么时候 freeze，和 ChatAgent 的 `when` 判断如何配合；
- input witness 如何记录“某一步实际消费了哪个素材版本”，以及它如何支撑 rewind；
- slot revision 的 selected / stale / list_index / sort_order 语义；
- Go 的 task outbox 如何保证“任务被接受但执行器崩溃”时仍能恢复；
- DriverAgent fallback 在什么情况下退化成 dynamic 模式。
